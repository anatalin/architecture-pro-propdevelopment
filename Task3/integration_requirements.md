# Требования к внешней интеграции сервисов «Умный дом»

Документ задаёт требования к интеграции PropDevelopment с платформой партнёра для интеллектуального домофона и шлагбаума. Он дополняет две диаграммы:

- [диаграмма контекста](smart_home_context.drawio);
- [обновлённая диаграмма контейнеров](PropDevelopment_C4_containers_smart_home.drawio).

Описание API партнёра у нас пока нет, поэтому документ фиксирует, что партнёр должен обеспечить, а не как он это уже делает. Все числовые значения (сроки, лимиты, срок хранения) являются предложением для согласования с партнёром, если рядом не указан закон. Юридические пункты должен подтвердить юрист.

## 1. Ключевые решения

| Решение | Почему |
| --- | --- |
| **PropDevelopment определяет, кому разрешён доступ, а партнёр исполняет.** Источник истины о правах находится в `smart-access-service` | Право на проход зависит от собственности, которую знает CRM. Смена собственника должна автоматически отзывать доступ |
| **Биометрия хранится только у партнёра.** PropDevelopment хранит согласие, статус и обезличенный идентификатор | Биометрия относится к самой опасной категории данных из Task1. Если её нет в наших системах, её нельзя случайно передать в DWH или партнёрам |
| **Видео и фото идут напрямую** между приложением и платформой по одноразовому токену | Биометрия и видео не проходят через наши серверы, а мы не несём нагрузку на медиатрафик |
| **Новые сервисы и БД не входят в `tenant-core-app` и CDC** | В Task2 выявлена передача сырых данных в DWH без ограничений. Новые чувствительные данные не должны туда попасть |
| **Весь обмен с платформой идёт через `integration-gateway`** | Task2 показала, что нет единых политик и точки контроля партнёрских API. Шлюз закрывает этот разрыв для новых сервисов, а на втором этапе и для существующих партнёров |
| **Адаптер платформы является модулем `smart-access-service`** | Партнёр пока один, отдельный сервис не окупит своей поддержки. Адаптер выделяется, когда появится второй партнёр |
| **Распознавание работает на стороне партнёра по переданному списку разрешений** | Открытие не должно зависеть от доступности наших сервисов и задержек сети |

## 2. Изменения в ландшафте систем

| Элемент | Статус | Что меняется |
| --- | --- | --- |
| `smart-access-service` | Новый | Права жильцов, гостевые пропуска, госномера, согласия, команды открытия, журнал, адаптер платформы |
| `smart-access-db` | Новый | Права, согласия, госномера, журнал событий. Биометрии нет, связи с DWH нет |
| `integration-gateway` | Новый | Единая точка входа и выхода для внешних платформ |
| Firewall на канале партнёра | Новый | Ограничивает обмен адресами партнёра |
| Витрина сервисов для собственников | Изменён | Экраны домофона и шлагбаума, WebRTC, согласие на биометрию, приём push |
| CRM | Изменён | Отдаёт данные о собственниках и квартирах, публикует событие смены собственника. Менеджер подключает дома и устройства через CRM |
| `auth-service-1` (Keycloak) | Изменён | Роль жильца, подтверждение входа MFA для чувствительных операций |
| Жилец | Новый пользователь | Получает права от собственника и работает через то же приложение |
| Платформа партнёра, домофоны и шлагбаумы, сервисы push | Новые внешние системы | См. диаграмму контекста |

## 4. Протоколы аутентификации и авторизации

### 4.1. Выбранные протоколы

| Канал | Аутентификация | Авторизация | Срок действия |
| --- | --- | --- | --- |
| Приложение → `smart-access-service` | OpenID Connect, Authorization Code + PKCE через Keycloak | JWT, роли и атрибуты (см. 4.2) | Access-токен 5–15 минут, refresh-токен с ротацией |
| Чувствительные операции в приложении | Повторный вход с MFA или биометрией телефона (step-up, проверка `acr`) | Отдельная проверка операции | Подтверждение до 5 минут |
| `smart-access-service` → CRM | OAuth 2.0 Client Credentials через Keycloak, внутри контура mTLS | Узкие scope только на чтение нужных данных | До 15 минут |
| Менеджер → CRM | Существующая аутентификация через AD, MFA для операций с устройствами | Роль и привязка к домам | По корпоративной политике |
| `integration-gateway` → платформа партнёра | mTLS + OAuth 2.0 Client Credentials, токен привязан к сертификату (RFC 8705) | Scope: `access.read`, `access.write`, `door.command`, `session.create`. Область ограничена подключёнными домами | До 15 минут |
| Платформа партнёра → `integration-gateway` | mTLS + подпись тела запроса (HMAC-SHA-256 или JWS) с временем и nonce | Разрешены только адреса партнёра и типы событий из контракта | Окно приёма 5 минут, повторы отклоняются |
| Приложение → платформа партнёра (видео, загрузка фото) | Одноразовый подписанный токен от платформы, выдаётся по запросу `smart-access-service` | Токен привязан к пользователю, вызову или загрузке и устройству | До 60 секунд на подключение |
| Устройство → платформа партнёра | Сертификат устройства (X.509, mTLS или эквивалент) | Устройство привязано к одному дому | Ротация по политике партнёра |
| `smart-access-service` → push-сервисы | Ключи или токены APNs и FCM через шлюз | Только отправка | По правилам сервисов |

Basic Auth, бессрочные API-ключи и передача токенов в URL запрещены.

### 4.2. Модель авторизации

Решение о праве принимает `smart-access-service` на каждый запрос. Роль проверяется вместе с атрибутами: дом, подъезд, квартира, устройство и срок действия. Идентификатор дома берётся из токена и базы прав, а не из параметров запроса клиента.

| Роль | Что доступно | Ограничения |
| --- | --- | --- |
| Собственник | Вызовы, открытие, журнал своей квартиры, управление жильцами, госномерами и пропусками | Только свои квартиры. Права снимаются при смене собственника |
| Жилец | Вызовы, открытие, своя биометрия и свой госномер | Права выдаёт собственник и может задать срок |
| Гость | Разовый или временный пропуск, биометрия не применяется | Срок задаётся обязательно, в приложение гость не входит |
| Менеджер | Подключение домов и устройств, техническое состояние, журнал по запросу | Нет доступа к видео и биометрии. Операции журналируются |
| Партнёр (система) | Операции только по scope и подключённым домам | Нет доступа к данным других партнёров и к Ф. И. О. |

### 4.3. Дополнительные правила

| ID | Требование | Приоритет |

| AUTH-02 | Открытие по звонку разрешается только при активном вызове. Удалённое открытие без вызова требует подтверждения на телефоне | Обязательно |

## 5. Организация взаимодействия

### 5.1. Принципы

| ID | Требование | Приоритет |
| --- | --- | --- |
| INT-01 | Все сообщения между предприятием и платформой проходят через `integration-gateway`. Исключения: медиапоток и загрузка фото, которые идут напрямую по токену | Обязательно |
| INT-02 | Команды и управление правами работают через синхронный REST + JSON, события приходят через подписанные webhook | Обязательно |
| INT-03 | Контракты описаны в OpenAPI 3 и AsyncAPI, версионируются (`/v1`), проходят контрактные тесты. О несовместимом изменении партнёр предупреждает минимум за 6 месяцев | Обязательно |
| INT-04 | Запись и команды идемпотентны по `Idempotency-Key`. Каждое событие имеет уникальный идентификатор и обрабатывается один раз | Обязательно |
| INT-05 | Изменения прав передаются через transactional outbox: запись в БД и постановка в очередь на отправку выполняются атомарно | Обязательно |
| INT-06 | Для исходящих вызовов настроены тайм-ауты, повторы с нарастающей задержкой и circuit breaker. Необработанные сообщения попадают в очередь разбора, и по ним приходит оповещение | Обязательно |
| INT-07 | Партнёр повторяет недоставленные webhook до 24 часов и даёт API для запроса пропущенных событий | Обязательно |
| INT-08 | Раз в сутки права сверяются с платформой по контрольным суммам. Лишние права на платформе немедленно отзываются, расхождение вызывает оповещение | Обязательно |
| INT-09 | В каждом запросе передаётся `traceparent` или другой идентификатор трассировки, чтобы проход можно было проследить в обеих системах | Обязательно |
| INT-10 | Партнёр предоставляет тестовую среду с эмуляцией устройств, данными без реальных ПДн и лимитами как в бою | Обязательно |
| INT-11 | Шлюз проверяет схему запросов и ограничивает частоту. Лимиты согласуются для каждого типа операций | Обязательно |

### 5.2. Основные сценарии

| Сценарий | Как проходит | Что важно |
| --- | --- | --- |
| Вызов и открытие по звонку | 1. Посетитель звонит, устройство передаёт вызов на платформу.<br>2. Платформа присылает webhook через шлюз.<br>3. `smart-access-service` определяет получателей и отправляет push без ПДн.<br>4. Приложение запрашивает сеанс, получает одноразовый токен и подключается к видео напрямую.<br>5. Пользователь нажимает «Открыть», сервис проверяет право и активный вызов и отправляет команду.<br>6. Платформа присылает результат | Открытие связано с конкретным вызовом. Отвечает первый из пользователей квартиры |
| Подключение распознавания лица | 1. Пользователь проходит MFA и подписывает согласие, сервис его сохраняет.<br>2. Сервис запрашивает у платформы одноразовую ссылку для загрузки.<br>3. Приложение отправляет фото напрямую на платформу.<br>4. Платформа проверяет живость, создаёт шаблон и удаляет фото.<br>5. Webhook сообщает статус | PropDevelopment видит только статус и идентификатор |
| Проход по лицу | 1. Камера передаёт кадр, платформа сравнивает его со списком разрешённых для этой двери.<br>2. При совпадении платформа открывает дверь.<br>3. Webhook передаёт событие в журнал | Решение принимается у партнёра по нашему списку |
| Въезд по госномеру | 1. Собственник или жилец добавляет номер, гостевой номер получает срок действия.<br>2. Сервис передаёт номер и срок платформе.<br>3. Камера распознаёт номер, платформа открывает шлагбаум.<br>4. Webhook передаёт событие в журнал | Срок гостевого номера проверяет сама платформа |
| Смена собственника | 1. CRM публикует событие в Kafka.<br>2. Сервис отзывает права по квартире и связанные пропуска.<br>3. Сервис передаёт отзыв платформе и удаляет шаблоны бывших жильцов.<br>4. Платформа подтверждает выполнение | Самая важная проверка: бывший собственник не должен попасть в дом |

### 5.4. Качество сервиса и работа при сбоях

| ID | Показатель или сбой | Значение или поведение |
| --- | --- | --- |
| NFR-01 | Доступность API платформы | Не ниже 99,9 % в месяц |
| NFR-02 | Время ответа API | 95 % запросов не дольше 500 мс |
| NFR-03 | Команда открытия от нажатия до срабатывания | Не дольше 2 секунд |
| NFR-04 | От распознавания до открытия | Не дольше 2 секунд |
| NFR-05 | Push о вызове на стороне PropDevelopment | Отправка не дольше 1 секунды после получения webhook |
| NFR-06 | Отзыв прав на устройстве | Не дольше 60 секунд |
| NFR-07 | Недоступны сервисы PropDevelopment | Распознавание работает по последнему списку, события накапливаются у партнёра, сроки временных пропусков соблюдаются |

## 6. Условия приёмки

Запуск в пилотном доме возможен после выполнения всех условий:

1. Подписаны договор поручения, требования SEC-01–SEC-13 и план реагирования на инциденты с партнёром.
2. Внешний пентест интеграции не выявил критических и высоких уязвимостей, включая доступ к данным другого дома.
3. Контрактные тесты проходят, сценарии из раздела 5.2 проверены на тестовой среде.
4. Проверены отказы из раздела 5.4 и отзыв прав при смене собственника.
5. Проверка живости подтверждена независимым отчётом и испытанием на объекте.
6. Журналы и оповещения поступают в мониторинг, специалист по ИБ проверил их и согласовал запуск.
